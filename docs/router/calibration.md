# Router calibration

`phm router-calibration --jobs jobs.jsonl [--posthog runs.json] [--json]` reads local files and prints Markdown by default or JSON with `--json`. It makes no network requests. It reads the fleet jobs-ledger dialect (`metrics/jobs.jsonl`): job ids take `job`, `job_id`, `jobId` or `id`; lifecycle events take `event`, `type` or `kind` (`published` folds to `publish`); stamps take `ts`, `timestamp`, `at`, `time`, `mergedAt`, `closedAt`, `recordedAt` or `updatedAt`; lanes take `lane`, `pool` or `arm`; terminal phases take `phase`, `state`, `outcome`, `status`, `result` or `conclusion`. Reward-signal rows (`reward-signal.v1`, e.g. `metrics/reward-signals.jsonl`) are also accepted as complete per-job outcome records.

Lifecycle events are `launch` and `batch_claim` (a dispatch opens an attempt), `finish` and `task_outcome` (an attempt closes), `publish`, and the outcome-bearing events `outcome`, `merged`, `closed`, `resolved`, `resolution` and `result`. A job may launch more than once: retries are separate attempts, and the newest dispatch provably at or before the recorded outcome supplies the arm, start time and predictions; the finish inside that attempt's window supplies the end time, tokens and wall time. Dispatches after the outcome belong to a later attempt and do not steal its attribution. `fleet.session-pool.v1` rows, `RQ-BATCH-*` session ids, `claim` rows and other operational events are ignored. Unrecognized events are ignored, but a nonempty ledger with no recognized events is rejected.

A merge verdict comes from `merged: true`, a `merged`/`closed` event name, or a terminal phase on an outcome event — including `metrics-outcomes-reconciler` rows, the only publish-shaped rows allowed to carry one. `MERGED` is positive; `CLOSED`, `NOT_MERGED`, `REJECTED` and `FAILED` are negative; a boolean `merged` is also accepted. A merge a later revert row postdates did not hold and counts as not merged. Two verdicts at the same instant that disagree are rejected as conflicting. Publishing, unknown outcomes (`OPEN`, `PENDING`, `DONE-NOOP`, …) and missing outcomes are not evidence of a merge or failure; unresolved rows without dispatch evidence are dropped rather than counted.

Use numeric `predicted_merge_rate` (probability from 0 to 1), `predicted_tokens`, and `predicted_wall_time_ms` for predictions — recorded on the winning dispatch row, with the newest value on any recognized row as fallback. Actual usage is `tokens`, `total_tokens`, `tokens_total` or wall time from `wall_time_ms`, `duration_ms`, or dispatchd's `wall_s` (seconds, converted to ms); a finish and launch with parseable stamps also supply wall time when no recorded value exists. Camel-case equivalents are accepted.

The optional PostHog export is a JSON array or an object with a `results` array; each row is a run or has a `properties` object. Join by `job_id` or `jobId`, using the same numeric fields. Unmatched rows are counted. Conflicting values are rejected rather than silently double-counted. PostHog export input must represent one run per job or contain consistent duplicate observations.

Each predicted / actual average uses only jobs with both values, with the paired count shown alongside it. Brier is the mean squared difference between each recorded merge probability and its binary resolved outcome for that same population. `resolved` counts all known outcomes, including jobs without predictions. Missing pairs produce null in JSON and `n/a` in Markdown. These are descriptive statistics of recorded evidence, not proof that the sample is representative. The files supplied by the operator determine schema compatibility and coverage.
